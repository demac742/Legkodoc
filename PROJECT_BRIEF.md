# Техническое задание: онлайн-сервис заполнения юридических документов

## 1. Суть проекта

Проект — это простой онлайн-сервис для быстрого заполнения, формирования и скачивания лёгких юридических документов.

Сервис предназначен для физических лиц, которым нужен понятный способ оформить документ без похода к юристу, без поиска Word-шаблонов в интернете и без сложного личного кабинета.

Пользователь выбирает документ, отвечает на понятные вопросы, сервис автоматически собирает PDF-документ.

Бесплатная версия доступна с водяным знаком. Чистая версия PDF доступна после разовой оплаты.

Проект не является сложным SaaS на этапе MVP. Это сервис разовой покупки документа.

## 2. Главный пользовательский сценарий

Главный поток:

Главная страница → Каталог документов → Страница документа → Конструктор документа → Ответы на вопросы → Сформировать PDF → PDF с водяным знаком → Оплата → PDF без водяного знака.

Пользователь должен проходить путь без регистрации, подписки и личного кабинета.

## 3. Целевая аудитория

Стартовый фокус — физические лица.

Пользователи:

- люди, которым нужна расписка, договор, заявление, жалоба или доверенность;
- люди, которые не хотят идти к юристу ради простой задачи;
- люди, которым нужен понятный документ быстро;
- люди, которые примерно понимают, что делать с документом дальше, но хотят заполнить его аккуратно;
- пользователи, ищущие в поиске образец документа, PDF или онлайн-заполнение.

На старте не фокусироваться на:

- ООО;
- сложных B2B-договорах;
- корпоративном документообороте;
- подписках для бизнеса;
- личных кабинетах для компаний.

## 4. Позиционирование

Сервис должен восприниматься как простой и надёжный помощник в оформлении лёгких юридических документов.

Основная формулировка:

“Заполните юридический документ онлайн за несколько минут. Ответьте на простые вопросы и скачайте готовый PDF.”

Дополнительные смыслы:

- без регистрации;
- без подписки;
- понятные вопросы;
- готовый PDF;
- бесплатный PDF с водяным знаком;
- чистый PDF после разовой оплаты;
- инструкция, что делать с документом после скачивания.

## 5. Бизнес-модель

Модель монетизации — разовая покупка PDF без водяного знака.

Пользователь может бесплатно сформировать и скачать PDF с водяным знаком.

Чтобы скачать PDF без водяного знака, пользователь оплачивает документ.

У каждого документа должна быть своя цена.

Пример цен:

- простые документы — 49 ₽;
- средние документы — 99 ₽;
- более сложные документы — 149 ₽.

Цена должна храниться в конфигурации каждого документа.

## 7. Структура сайта

Главная страница должна быстро объяснять, что делает сервис.

Обязательные блоки:

- первый экран с понятным заголовком;
- краткое описание сервиса;
- кнопка “Выбрать документ” или “Заполнить документ”;
- блок популярных документов;
- блок “Как это работает”;
- блок преимуществ;
- объяснение модели оплаты;
- SEO-текст;
- ссылки на категории документов.

Пример первого экрана:

“Заполните юридический документ онлайн. Ответьте на простые вопросы и получите готовый PDF за несколько минут.”

### Каталог документов

Каталог должен содержать карточки документов.

Карточка документа должна включать:

- название документа;
- короткое описание;
- категорию;
- цену PDF без водяного знака;
- кнопку “Заполнить онлайн”.

Категории:

- деньги и долги;
- автомобиль;

- услуги;

- суд и приставы;

На странице документа должны быть:

- H1 с названием документа;

- кнопка “Заполнить онлайн”;

- как заполнить документ;
- что делать после скачивания;
- FAQ;
- похожие документы;
- юридический дисклеймер.

Примеры URL:

- /documents/raspiska-o-poluchenii-deneg
- /documents/dogovor-zayma
- /documents/dogovor-kupli-prodazhi-avtomobilya

## 8. Конструктор документа

Конструктор должен работать по логике онлайн-заполнения документа.

Пользователь должен не просто видеть длинную форму, а проходить через документ и отвечать на вопросы внутри логики документа.

Ориентир по механике:

документ → блок вопроса → выбор варианта → следующий блок → сформированный PDF.

Можно вдохновляться механикой dogovor.ru и похожих конструкторов документов, но нельзя копировать:

- дизайн;
- тексты;
- бренд;
- CSS;
- визуальные элементы;
- юридические шаблоны;
- структуру страниц конкурента.

Нужно взять только общий принцип: пользователь выбирает условия документа через понятные вопросы.

## 10. Сохранение данных пользователя

Данные пользователя должны сохраняться после закрытия или обновления страницы.

Для MVP использовать localStorage.

Требования:

- пользователь начал заполнять документ;
- закрыл вкладку или обновил страницу;
- вернулся позже;
- введённые данные восстановились;
- данные сохраняются отдельно для каждого документа.

Пример ключа:

document-draft:raspiska-o-poluchenii-deneg

На MVP не нужен личный кабинет и серверное хранение черновиков.

## 11. PDF-логика

После заполнения документа пользователь нажимает “Сформировать PDF”.

Система должна сформировать PDF-документ.

### Бесплатный PDF

Бесплатный PDF должен:

- всегда содержать водяной знак;
- иметь водяной знак на каждой странице;
- быть читаемым;
- позволять пользователю проверить документ;
- быть доступным без оплаты.

Водяной знак должен быть не одной маленькой надписью, а паттерном по всей странице.

Требования к водяному знаку:

- текст водяного знака: “ЛЕГКОДОК”;
- водяной знак должен повторяться по всей странице;
- располагаться по диагонали;
- быть крупным;
- быть полупрозрачным;
- выглядеть аккуратно и эстетично;
- не должен полностью перекрывать текст документа;
- текст документа должен оставаться читаемым;
- водяной знак должен быть на каждой странице PDF.

Визуальная идея:

Как будто на фоне документа по всему листу наискосок повторяется “ЛЕГКОДОК”, светло и прозрачно, но заметно.

### Платный PDF

PDF без водяного знака:

- доступен только после оплаты;
- не должен выдаваться только по frontend-состоянию;
- должен открываться или генерироваться после backend-подтверждения оплаты;
- должен скачиваться сразу после успешной оплаты.

Пользователь не должен иметь возможность получить чистый PDF без подтверждённой оплаты.

## 12. Оплата

Оплата нужна только для снятия водяного знака.

Логика:

1. Пользователь сформировал PDF с водяным знаком.
2. Пользователь видит кнопку “Скачать без водяного знака за 49 ₽” или другую цену документа.
3. Пользователь переходит на оплату.
4. Backend создаёт заказ.
5. После успешной оплаты backend подтверждает статус.
6. Пользователь сразу скачивает PDF без водяного знака.

Статусы заказа:

- created;
- pending_payment;
- paid;
- failed;
- expired.

На MVP не делать:

- отправку PDF на email;
- личный кабинет;
- историю документов;
- подписки;
- тарифы.

## 13. Визуальный стиль

Визуальный стиль должен быть строгим, лёгким и современным.

Основная палитра:

- чёрный;
- белый;
- серый.

Референс проекта — современный онлайн-сервис документов.

Интерфейс должен ощущаться как простой, спокойный и доверительный юридический сервис.

Визуальное направление:

- белый или светло-серый фон;
- тёмный текст;
- чёрно-белая/серая палитра;
- карточки документов;
- пошаговая форма заполнения;
- блоки доверия;
- аккуратный PDF-превью;
- спокойный юридический тон;
- много воздуха;
- понятная типографика;
- минимум декоративных элементов.

Сайт не должен выглядеть как тяжёлый SaaS, яркий стартап-лендинг или старый государственный портал.

Не использовать:

- яркие цвета;
- агрессивные градиенты;
- тяжёлые картинки;
- перегруженный интерфейс;
- сложные анимации;
- зелёный стиль как у dogovor.ru;
- копирование дизайна dogovor.ru.

Главное ощущение интерфейса:

“Я быстро и спокойно заполняю важный документ, понимаю каждый шаг и доверяю результату.”

## 15. Юридические тексты и ответственность

Юридические тексты документов пишет и проверяет владелец проекта.

Codex не должен самостоятельно менять юридический смысл документов без отдельной задачи.

Codex может:

- создавать структуру шаблона;
- подставлять переменные;
- делать форму;
- делать PDF;
- делать SEO-обвязку;
- делать интерфейс.

Codex не должен:

- утверждать, что документ юридически корректен;
- менять смысл юридического текста;
- удалять условия из документа;
- добавлять юридические условия от себя без согласования.

На сайте обязательно должен быть дисклеймер:

“Документ является типовым шаблоном и не заменяет индивидуальную юридическую консультацию. Перед использованием проверьте данные и убедитесь, что документ подходит для вашей ситуации.”

Для некоторых документов нужно указывать предупреждения.

Например:

“Ненотариальная доверенность подходит не для всех случаев. В отдельных ситуациях может потребоваться нотариальная доверенность.”

## 19. MVP

MVP считается готовым, если:

1. Есть главная страница.
2. Есть каталог документов.
3. Есть страница хотя бы одного документа.
4. Есть конструктор документа.
5. Пользователь может заполнить документ.
6. Данные сохраняются в localStorage.
7. Пользователь может сформировать PDF.
8. Бесплатный PDF всегда содержит водяной знак “ЛЕГКОДОК” по всей странице.
9. Есть кнопка оплаты чистого PDF.
10. После оплаты пользователь получает PDF без водяного знака.
11. Есть базовые SEO-настройки.
12. Есть юридический дисклеймер.
13. Сайт адаптирован под мобильные устройства.

## 20. Что не делать в MVP

На старте не делать:

- регистрацию;
- авторизацию;
- личный кабинет;
- подписки;
- тарифные планы;
- историю документов;

- совместное редактирование;
- согласование с контрагентом;

- сложный визуальный редактор документа.

## 21. Будущее развитие проекта

Этот раздел описывает будущие возможности. Не реализовывать их в MVP, если задача явно не просит.

Архитектуру проекта нужно делать так, чтобы в будущем можно было без полного переписывания добавить следующие возможности.

### 21.1 Простое добавление новых документов

Новые документы должны добавляться через конфигурации, а не через переписывание всей логики.

Для каждого документа должны быть отдельные данные:

- id;
- slug;
- title;
- category;
- description;
- price;
- fields;
- SEO-данные;
- шаблон документа;
- правила генерации PDF;
- подсказки для пользователя;
- предупреждения и дисклеймеры.

Цель: новый документ можно добавить как новый конфиг + текст шаблона + список полей.

### 21.2 Расширение конструктора

В будущем конструктор должен поддерживать:

- условные вопросы;
- разные сценарии внутри одного документа;
- скрытие и показ блоков в зависимости от ответов;
- повторяемые блоки, например несколько участников, товаров, услуг или платежей;
- проверку обязательных полей;
- подсказки рядом с вопросами;
- предпросмотр документа перед PDF.

### 21.3 Черновики

В MVP черновики сохраняются в localStorage.

В будущем нужно предусмотреть возможность серверного сохранения черновиков, чтобы пользователь мог:

- вернуться к документу позже;
- продолжить заполнение с другого устройства;
- видеть список своих черновиков в личном кабинете;
- удалять черновики;
- редактировать черновики.

### 21.4 Личный кабинет

В MVP личный кабинет не нужен.

В будущем можно добавить личный кабинет, где пользователь сможет:

- видеть купленные документы;
- повторно скачать оплаченный PDF;
- продолжить черновики;
- хранить свои данные для автозаполнения;
- видеть историю оплат;
- управлять профилем.

Архитектура не должна мешать добавлению личного кабинета позже.

### 21.5 Автозаполнение и вычисляемые поля

В будущем нужно поддержать вычисляемые поля.

Примеры:

- пользователь вводит сумму цифрами;
- система автоматически подставляет сумму прописью;
- пользователь вводит дату;
- система может подставить дату в нужном формате;
- пользователь вводит ФИО;
- система может использовать ФИО в разных падежах, если это будет реализовано;
- пользователь вводит данные одной стороны;
- эти данные автоматически подставляются во все нужные места документа.

Пример:

50 000 ₽ → “пятьдесят тысяч рублей”

Такие значения должны генерироваться автоматически, чтобы пользователь не вводил одно и то же несколько раз.

### 21.6 Повторное использование данных

В будущем пользователь должен иметь возможность сохранить типовые данные:

- ФИО;
- паспорт;
- адрес;
- телефон;
- email;
- реквизиты;
- данные автомобиля;
- данные квартиры;
- данные контрагента.

Эти данные можно будет использовать для автозаполнения новых документов.

В MVP это не реализовывать, но структуру данных документов делать так, чтобы повторное использование было возможно позже.

### 21.7 Расширение форматов

В MVP продаётся только PDF.

В будущем можно добавить:

- DOCX;
- печатную версию;
- отправку документа на email;
- хранение документа в личном кабинете.

Не реализовывать это в MVP.

### 21.8 Админка

В MVP админка не нужна.

В будущем можно добавить админку для управления:

- списком документов;
- ценами;
- SEO-текстами;
- шаблонами;
- статусами документов;
- FAQ;
- предупреждениями;
- юридическими дисклеймерами.

### 21.9 Платёжные возможности

В MVP нужна разовая оплата за один PDF.

В будущем можно добавить:

- разные цены по категориям;
- промокоды;
- бесплатные документы;
- пакеты документов;
- повторное скачивание оплаченного документа;
- возвраты;
- чеки;
- интеграцию с несколькими платёжными провайдерами.

### 21.10 Главный принцип будущего развития

Будущие функции не должны усложнять MVP.

Сначала нужно сделать один стабильный рабочий поток:

Каталог → документ → заполнение → PDF с водяным знаком → оплата → PDF без водяного знака.

Но код и структура проекта должны быть достаточно аккуратными, чтобы позже можно было добавить черновики, личный кабинет, автозаполнение, новые документы и расширенные сценарии без полного переписывания проекта.

## 22. Главная цель проекта

Главная цель первой версии — доказать, что пользователь может:

1. Найти нужный документ.
2. Понять, подходит ли он ему.
3. Заполнить документ через вопросы.
4. Получить PDF с водяным знаком “ЛЕГКОДОК”.
5. Оплатить чистую версию.
6. Скачать PDF без водяного знака.

Сначала нужно сделать один идеальный рабочий сценарий, а потом масштабировать сервис на остальные документы.

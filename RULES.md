# Правила проекта

## 1. Дисциплина изменений

- Делай маленькие, целенаправленные изменения.
- Не переписывай архитектуру, не переименовывай файлы, не меняй маршруты и не рефакторь несвязанный код без явной задачи.
- Реализацию MVP делай простой, но не блокируй будущее расширение (конфигурируемые документы, без хардкода логики под каждый документ).

## 2. Границы MVP – НЕЛЬЗЯ делать

- Аккаунты, логин, личный кабинет
- Подписки, регулярные платежи
- Историю документов, повторные скачивания
- Экспорт в DOCX / Word
- Админку
- Серверные черновики (используй только localStorage)
- Профили с повторяющимся автозаполнением
- Отправку на email
- Промокоды или пакеты документов

## 3. Правила UI

**Стиль:** белый/светло-серый фон, тёмный текст, чёрно-бело-серая палитра, чистый макет, спокойный тон.

**Запрещено:**  
- зелёный стиль dogovor.ru  
- яркие акцентные цвета  
- тяжёлые иллюстрации  
- перегруженный интерфейс  
- пафосные или сложные анимации (если только не попросили явно)

Не меняй вёрстку, CSS, компоненты или пользовательский поток, если задача не связана именно с UI.

## 4. Правила конструктора

- Поток: документ → блок вопроса → ответ → следующий блок → сгенерированный PDF.
- Опыт должен быть с подсказками, а не длинной скучной формой.
- Шаблоны документов должны быть конфигурируемыми (никаких хардкодных документов).
- Не копируй дизайн dogovor.ru, тексты, CSS, шаблоны или брендинг.

## 5. Правила PDF и оплаты

**Бесплатный PDF** должен:
- всегда содержать водяной знак «ЛЕГКОДОК» на каждой странице;
- повторять водяной знак по диагонали;
- сохранять основной текст читаемым.

**Платный (чистый) PDF** должен:
- не иметь водяного знака;
- быть доступен **только после подтверждения оплаты на бэкенде**;
- никогда не разблокироваться по состоянию фронтенда.

**Типографика PDF:**
- короткие сокращения не должны оставаться одни в конце строки;
- ставь неразрывный пробел после `г.`, `ул.`, `д.`, `кв.`, `№` и похожих коротких обозначений;
- применяй общее правило типографики ко всем новым документам, а не локальный regex под один шаблон.

## 6. Правила юридического содержания

- Владелец проекта пишет и проверяет юридические тексты.
- Не меняй юридический смысл без явного указания.
- Не заявляй юридических гарантий.
- На страницах документов должен быть юридический дисклеймер, если он предусмотрен для этого документа.

## 7. Правила работы с данными (MVP)

- Черновики хранятся только в `localStorage`.
- Отдельный ключ для каждого документа (например, `document-draft:raspiska-o-poluchenii-deneg`).
- Для черновиков не нужен аккаунт.

## 8. Отчётность

После каждой задачи сообщай:
- изменённые файлы;
- что именно изменено (кратко);
- как протестировать вручную;
- любые риски или незавершённые части.

Не говори «готово», если сборка, линтер или ручная проверка заведомо не проходят.

## 9. Размер ответов (экономия токенов)

- **Не выводи целиком файлы**, если я явно не попросил полное содержимое.
- Показывай только изменённые блоки кода (в стиле diff или с плейсхолдерами `// ... неизменная часть ...`).
- Если файл большой, выводи только конкретные функции или строки, которые изменились.
- Старайся отвечать лаконично — не повторяй один и тот же код или объяснение несколько раз.
